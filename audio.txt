# 1. Executive verdict

I re-audited the current `master` branch of `addynoven/scheme-backend` as of September 3, 2026. The repository is substantially more ambitious and structured than a typical student backend: it has FastAPI modules, PostgreSQL/SQLAlchemy, Alembic migrations, JWT auth, RBAC, a rule engine, LLM tool-calling, SSE chat, OCR/document extraction, MinIO/S3, household modeling, ingestion/triage, and tests. The module boundaries are visible in the repository tree.

But there is an important distinction:

> **The architecture looks much more production-oriented than the actual security and consistency guarantees currently are.**

My current assessment:

| Area                             |  Score | Verdict                                                       |
| -------------------------------- | -----: | ------------------------------------------------------------- |
| Architecture / modularity        | 8.0/10 | Strong                                                        |
| API design                       | 6.5/10 | Good structure, serious access-control problems               |
| Authentication                   | 6.0/10 | JWT works, lifecycle is incomplete                            |
| Authorization / tenant isolation | 3.5/10 | **Critical problems**                                         |
| Database design                  | 7.0/10 | Fundamentally decent                                          |
| Transactions / consistency       | 5.5/10 | Too much commit-at-service-boundary behavior                  |
| Eligibility engine               | 7.0/10 | Clever architecture, but correctness risks                    |
| LLM architecture                 | 7.5/10 | Good tool-oriented direction                                  |
| Document/OCR security            | 5.5/10 | Sensitive-data handling needs hardening                       |
| Performance                      | 7.0/10 | Some very good ideas, some misleading optimizations           |
| Testing                          | 7.0/10 | Better than average, but important security paths are missing |
| Production readiness             | 5.0/10 | Not ready without security/consistency fixes                  |

### Overall: **6.2/10 production engineering**

For a serious portfolio/backend learning project, though, I would rate it around **8/10 in ambition and engineering direction**.

That distinction matters.

You are no longer building "CRUD FastAPI."

You are building a **policy/data platform with an AI interface on top**.

The next step is not adding more features. It is making the existing system *trustworthy*.

# 2. The biggest problem: authorization is not actually centralized

This is the most important thing I found.

Your admin router is protected correctly:

```python
router = APIRouter(
    prefix="/admin",
    tags=["Admin Management"],
    dependencies=[Depends(get_current_admin_user)],
)
```

So `/admin/*` is protected by the admin dependency.

But your ordinary auth router exposes management APIs that are **not protected at all**:

```python
@router.post("/users")
def create_user_endpoint(...)

@router.get("/users")
def list_users_endpoint(...)

@router.get("/users/{user_id}")
def get_user_by_id_endpoint(...)

@router.patch("/users/{user_id}")
def update_user_endpoint(...)

@router.delete("/users/{user_id}")
def delete_user_endpoint(...)
```

There is no `Depends(get_current_user)` on these endpoints.

That means your system effectively has:

```text
/admin/users
        -> protected

/users
        -> apparently public
```

This is not merely "API cleanliness."

It is an **authorization vulnerability**.

A remote caller can potentially enumerate users, retrieve users, modify users, or delete users depending on validation and database state.

### Severity: CRITICAL

This is the first thing I would fix.

You clearly intended this pattern:

```text

/users/me/profile
/users/me/facts
```

Those are properly authenticated.

But then you also expose:

```text
/users/{user_id}

```

without authentication.

That creates two authorization models simultaneously:

```text
resource owner model
        |
        +--> /users/me

arbitrary object-ID access model
        |

```

The second one defeats the first.

### First-principles rule

A resource containing personally identifiable citizen information should require one of:

```text

admin/operator
explicit delegated authority
```

Not:

```text

```

# 4. There is an IDOR problem in chat sessions

This is another major finding.

Your chat session retrieval intentionally falls back to querying the session **without the user filter**:

```python
query = select(ChatSession).where(ChatSession.id == session_id)

if user_id is not None:
    query = query.where(
        or_(
            ChatSession.user_id == user_id,
            ChatSession.user_id.is_(None)
        )
    )
```

Then:

```python
if not session:
    existing = db.scalar(
        select(ChatSession).where(ChatSession.id == session_id)
    )

    if existing:
        ...
        return existing
```

So if:

```text
User A owns session 123
User B requests session 123
```

the second query can find User A's session and return it.

The same logic is then used by:

```text
GET    /chat/sessions/{id}
PATCH  /chat/sessions/{id}
DELETE /chat/sessions/{id}
```

because all of those call `get_chat_session()`.

That means you have a serious potential cross-user chat-history access/modification vulnerability.

### Even worse

`delete_chat_session()` calls:

```python
session = get_chat_session(...)
db.delete(session)
```

So the same ownership bug can potentially turn into cross-user deletion.

### Severity: CRITICAL

This is more important than almost any performance issue in the project.

# 5. Your guest-session adoption logic is too trusting

You are intentionally supporting:

```text
guest
  |
  v
anonymous ChatSession
  |
  v
login
  |
  v
attach session to user
```

That's a reasonable product idea.

But your implementation essentially says:

```python
if existing.user_id is None and user_id is not None:
    existing.user_id = user_id
```

There is no proof that this anonymous session actually belongs to the authenticated user.

Because the session is identified by a numeric ID, ownership becomes:

```text
know ID
+
authenticate
=
claim guest session
```

That's not sufficient.

### Better design

Use a random opaque session identifier:

```text
chat session id
UUID / ULID
```

and maintain a guest ownership token:

```text
anonymous session
    |
    +-- guest_token_hash
    |
    +-- expires_at
```

Then:

```text
guest_token
      |
      v
claim session
      |
      v
authenticated user
```

Now the claimant needs the possession secret, not merely an integer identifier.

# 7. Your optional-auth dependency intentionally hides invalid tokens

This code is problematic:

```python
def get_current_user_optional(...):
    if not credentials:
        return None

    try:
        payload = decode_token(token)

        if payload.get("type") != "access":
            return None

        ...
    except Exception:
        return None
```

So:

```text
No token
    -> guest

Invalid token
    -> guest

Expired token
    -> guest

Malformed token
    -> guest

Wrong token type
    -> guest
```

These are semantically very different.

Imagine:

```http
Authorization: Bearer invalid-token
```

The client may believe it is authenticated, but your backend silently converts it into an anonymous request.

This makes debugging harder and can create authorization ambiguity.

### Better contract

For optional auth:

```text
missing Authorization
    -> guest

Authorization present + invalid
    -> 401
```

That distinction is extremely useful.

# 8. Refresh-token rotation is not really rotation

Your docs claim:

> "Token Rotation: POST /auth/refresh issues a new token pair"

And the service does generate a new pair.

But there is no server-side refresh-token state.

The server simply verifies:

```text
JWT
type == refresh
sub == user
exp valid
```

and issues another pair.

Therefore:

```text
Refresh Token A
       |
       v
Refresh Token B
```

does **not** invalidate A.

So:

```text
stolen Refresh Token A
```

can still be replayed until expiry.

### True rotation

You need something like:

```text
refresh_tokens
---------------------
id
user_id
token_hash
family_id
expires_at
revoked_at
replaced_by
created_at
```

Then:

```text
refresh A
    ->
revoke A
    ->
issue B
```

If A is used again:

```text
TOKEN REUSE DETECTED
    ->
revoke entire token family
```

That is much closer to production authentication.

# 12. The eligibility engine has a conceptual correctness problem

This is the most interesting technical part of your project.

You built:

```text
PostgreSQL
    |
    v
warm_up()
    |
    v
precompiled bitmasks
    |
    v
microsecond evaluation
```

That's a legitimately interesting architecture.

But the cache is only rebuilt in application startup:

```python
bitmask_engine.warm_up(db)
```

Now look at your admin API.

An admin can:

```text
create scheme
update scheme
delete scheme
add eligibility rule
delete eligibility rule
```

But those mutations do not refresh the engine.

So:

```text
PostgreSQL
    |
    | admin modifies rules
    v
Database = NEW

Bitmask engine
    |
    v
Memory = OLD
```

This creates a **split-brain eligibility system**.

The API may say:

```text
scheme has income <= 50000
```

while the eligibility engine still evaluates:

```text
old income <= 100000
```

until process restart.

### Severity: HIGH

This is much more important than your "microsecond" optimization.

# 16. Another hidden eligibility issue: multiple rules are treated as repeated exclusion

Your engine loops through all numeric rules:

```python
for rule in self.numeric_rules:
```

and independently excludes a scheme if a rule fails.

That is correct for:

```text
age >= 18
AND
age <= 35
```

provided both rules exist separately.

But the data model itself doesn't encode logical structure:

```text
AND
OR
NOT
groups
```

It's just:

```text
field_name
operator
rule_value
```

That means your engine can express simple conjunctions but will struggle with real-world policies such as:

```text
(age >= 18 AND income <= 200000)
OR
(disabled == true)
```

Real welfare policy gets complicated quickly.

### Recommendation

Eventually model rules as an expression tree:

```text
EligibilityExpression
    |
    +-- AND
         |
         +-- Rule
         +-- OR
               |
               +-- Rule
               +-- Rule
```

Don't implement that now unless required. But recognize the ceiling of the current model.

# 31. Your Gemini retry strategy can become expensive

Your chat service tries:


with:


```text

   |
   +--> model B
   |

```

```text

```

Right now model fallback and transient retry appear too intertwined.
